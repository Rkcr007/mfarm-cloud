00 — Orientation

What this day is for

One sentence: we are trying to make a real Appium test run green against a real Android device on our own infrastructure, once. Everything else is secondary.

Right now the repo has 333 passing tests and a complete-looking automation path in which the WebDriver hub has only ever spoken to a stub and the Appium supervisor has only ever supervised a fake. Phases 3 and 4 — artifacts, video, the web UI — all sit on top of that path. If it is wrong in some structural way, everything built on it gets reworked. So we prove it before we build more.

Why we need someone else's computer

Cuttlefish is Google's virtual Android device. It runs the real Android OS in a virtual machine, which means the machine running it must itself be able to run virtual machines. Three hard requirements:

  • Linux — not macOS.
  • x86_64 — Intel/AMD. Snapshot-restore is x86_64 only.
  • A working /dev/kvm — the kernel's virtualisation device.

Your MacBook is Apple Silicon, which is Arm, and macOS has no /dev/kvm. There is no workaround worth trying — emulating x86 in software to then run a VM inside it would be unusably slow. That is the whole reason we go to the cloud.

The jargon, once

Nested virtualisation is the cloud provider letting your virtual machine run virtual machines of its own. Normally they don't. It is a setting chosen when the machine is created and it cannot be switched on afterwards — get it wrong and you delete the machine and make a new one. This is the single most common way people lose an hour on day one.

Recommended order

Track A first, then Track B. Track A costs nothing and has no clock on it, so it is where you discover that a cvd flag changed upstream or that a package name moved — the boring failures. You then arrive at the paid box already knowing the flags work, and spend metered hours only on what a real machine can do: two devices, real Appium, numbers.

Track A also keeps paying afterwards. Once it passes, it becomes a scheduled CI job that tells you the day upstream Cuttlefish breaks our assumptions — which is otherwise the kind of thing you find out during a demo.

Track A's hard ceiling, stated plainly

GitHub's free runners for public repositories are 4 CPU cores / 16 GB RAM / ~14 GB free disk. For private repositories they are 2 cores / 7 GB, which will not boot Cuttlefish at all. Our repo is private, so Track A runs from a separate small public repo holding only the probe — no proprietary code. That is step A1.

02 — Definition of done

Milestones, in order of value

Do not treat this as one long day that either succeeds or fails. Each milestone is a real result you can stop at, write down, and destroy the machine. A day that ends at M2 is a good day.

Expectation setting

Your first session will probably end at M1, and that is a success. HANDOFF.md already predicts it: “Real Appium 2 + UiAutomator2 against real Cuttlefish. Expect disagreement.” Known issue 1 says our cvd flags are unverified and upstream moves. Finding out exactly how they are wrong is the product of this day. Budget two or three short sessions, not one heroic one.

03 — Before you touch anything

The money rules

Track A cannot cost money. Track B can, if you are careless. Four rules; the third is the one that actually catches people.

Read this twice
  1. Stay on the free trial. Never click “Activate full account” or “Upgrade”. While you are on the trial, Google will not charge your card — when the credit or the 90 days run out, your resources simply stop. That safety net disappears the moment you upgrade.
  2. The machine costs money only while it is running. Roughly ₹55–75 an hour for the size we want. An eight-hour session is under ₹600 of a ₹25,000 credit.
  3. Stopping the machine does not stop the disk bill. This is the classic surprise. A stopped VM bills nothing for CPU and keeps billing for its disk — a 150 GB disk is around ₹1,200 a month whether or not anything is running. Delete, don't stop. Step B10 shows how to keep your work anyway.
  4. Finish every session with step B11. Deleting the VM is not enough on its own; you must confirm no disks survived it.
Pausing mid-session, when you have to step away

If you are leaving the machine for more than an hour but are not finished with it, stop it rather than letting it idle at ₹55–75 an hour. The catch: gcloud compute instances stop fails from inside the VM with PERMISSION_DENIED … ACCESS_TOKEN_SCOPE_INSUFFICIENT, because a VM authenticates as its own service account and that account has no permission to stop instances. Run it from the Cloud Shell tab, where you are authenticated as yourself:

Cloud Shell
gcloud compute instances stop mfarm-lab --zone=asia-south1-c
gcloud compute instances list   # want STATUS: TERMINATED

Or, from inside the VM where it always works and needs no permissions at all, sudo poweroff. Powering off the guest moves the instance to TERMINATED and stops the compute bill just the same. The disk keeps billing either way — see rule 3.

Prices move and vary by region. Ignore the numbers above as gospel — the create-instance screen shows a live monthly estimate on the right-hand side, and that estimate is the one to trust.

Track A · GitHub Actions Free · no card

The free probe

Goal: answer “do our cvd flags boot a device on a stock Ubuntu machine?” without spending anything or entering a card, and leave behind a job that keeps answering it forever.

A2

The workflow

~10 minutes · the file that does the work

Save this as .github/workflows/cuttlefish-probe.yml. Read the comments — they say what each part is fighting.

.github/workflows/cuttlefish-probe.yml
name: Cuttlefish boot probe

# Manual button, plus a weekly run so we hear about upstream drift
# on a Monday rather than during a demo.
on:
  workflow_dispatch:
  schedule:
    - cron: "0 3 * * 1"

jobs:
  boot:
    runs-on: ubuntu-24.04
    timeout-minutes: 90

    steps:
      - uses: actions/checkout@v4

      # ---- THE GATE -------------------------------------------------
      # If this fails nothing else is worth running. GitHub's Linux
      # runners do expose /dev/kvm, but say so out loud rather than
      # letting a later step fail confusingly.
      - name: Gate — /dev/kvm must exist
        run: |
          set -eux
          ls -l /dev/kvm
          egrep -c '(vmx|svm)' /proc/cpuinfo
          sudo apt-get update -qq
          sudo apt-get install -y -qq cpu-checker
          sudo kvm-ok

      # ---- DISK -----------------------------------------------------
      # The runner has ~14 GB free and the Android image alone is
      # several GB. Deleting toolchains we do not use buys ~25 GB.
      # This is the step most likely to decide whether the job fits.
      - name: Reclaim disk
        run: |
          set -eux
          df -h /
          sudo rm -rf /usr/share/dotnet /usr/local/lib/android \
                      /opt/ghc /usr/local/share/boost \
                      /usr/local/share/powershell /usr/share/swift \
                      "$AGENT_TOOLSDIRECTORY" || true
          sudo apt-get clean
          df -h /

      # ---- INSTALL --------------------------------------------------
      # The bootstrap script ends phase 1 by asking for a reboot,
      # because group membership (kvm, cvdnetwork, render) does not
      # apply to a running shell. We cannot reboot a runner, so we let
      # phase 1 run, then re-enter the shell with the new groups via
      # `sg` instead of rebooting.
      - name: Install Cuttlefish (phase 1)
        run: ./spikes/bootstrap_cuttlefish.sh

      - name: Confirm the packages landed
        run: |
          set -eux
          dpkg -l | grep -i cuttlefish
          command -v cvd

      # ---- BOOT -----------------------------------------------------
      # `sg` starts a new shell with the group applied, which is the
      # reboot-free equivalent of what phase 2 wants. Nested `sg` calls
      # are ugly and are exactly the part most likely to need fiddling;
      # if it misbehaves, `sudo chmod 666 /dev/kvm` is the usual
      # shortcut people reach for in CI.
      - name: Fetch image and boot one device (phase 2)
        run: |
          set -eux
          sg cvdnetwork -c "sg render -c \"sg kvm -c './spikes/bootstrap_cuttlefish.sh'\""

      # ---- THE REAL QUESTION ----------------------------------------
      # Snapshot/restore needs these two flags specifically, and the
      # smoke test in the script does not use them. This step is the
      # actual reason the probe exists.
      - name: Boot with the snapshot-capable flags
        run: |
          set -eux
          cd "$HOME/cf/image"
          sg cvdnetwork -c "sg render -c \"sg kvm -c '
            cvd start --daemon \
              --gpu_mode=guest_swiftshader \
              --enable_virtiofs=false \
              --report_anonymous_usage_stats=n
          '\""
          for i in $(seq 1 300); do
            if adb -s 0.0.0.0:6520 shell getprop sys.boot_completed 2>/dev/null | grep -q 1; then
              echo "BOOTED with guest_swiftshader after ${i}s"; exit 0
            fi
            sleep 1
          done
          echo "did not reach boot_completed in 300s"; exit 1

      # Always collect the logs — a failed run is the informative one.
      - name: Collect logs
        if: always()
        run: |
          mkdir -p /tmp/out
          cp /tmp/cf_*.log /tmp/out/ 2>/dev/null || true
          cp -r "$HOME"/cf/image/cuttlefish/instances/*/logs /tmp/out/ 2>/dev/null || true
          df -h / > /tmp/out/disk.txt

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: cuttlefish-logs
          path: /tmp/out
Two honest caveats

The sg nesting is my best guess, not verified. The bootstrap script was written for a real machine that can reboot. This is the step I expect you to have to adjust, and the probe existing at all is what makes adjusting it free.

Pin third-party actions to a SHA. Our own ci.yml enforces this and the reasoning applies here too — a tag can be moved to any commit. The two actions above are GitHub's own; if you add mxschmitt/action-tmate for debugging, pin it.

A3

Run it and read the result

~30–60 minutes, unattended

Push the workflow, then on GitHub go to Actions → Cuttlefish boot probe → Run workflow. Then walk away; it is not interactive.

Track B · Google Cloud Trial credit

The real workbench

Why Google rather than AWS, briefly: the free trial is $300 against roughly $100–200 of AWS credits; the trial stops rather than billing your card; nested virtualisation has worked here for years rather than months; and Cuttlefish's own reference environment is Google Compute Engine — AOSP ships a tool specifically for building a GCE host image. For this workload it is the better-trodden path.

B1

Account and project

~10 minutes · one-time

  1. Go to cloud.google.com and click Get started for free.
  2. Sign in with a Google account and enter a card. It is used to prove you are a real person and will not be charged unless you later choose to upgrade.
  3. You now have $300 of credit, valid 90 days. The console shows the balance and days remaining on its home page — glance at it each session.
  4. Create a project named mfarm-lab. A project is a box that holds resources so you can delete all of them together.
Do not click this

The console will repeatedly offer “Activate full account” or “Upgrade”. Do not. It converts you to pay-as-you-go and removes the stop-instead-of-charge protection that makes this exercise free. There is no benefit to you during R&D.

B2

Set a budget alarm before creating anything

~5 minutes · do this first, not last

In the console search bar type Budgets & alerts, then Create budget. Scope it to the mfarm-lab project, set the amount to $20, and tick alert thresholds at 25%, 50%, 100%.

What a budget does and does not do

A budget emails you. It does not stop anything. Automatically cutting off spending needs extra plumbing that is not worth building for an R&D week. Treat the email as a smoke alarm: it tells you that you forgot to delete something, and step B11 is what actually prevents that.

B3

Create the box

~5 minutes · the one screen that matters

Easiest path: open Cloud Shell — the >_ icon at the top right of the console. It is a free browser terminal with the gcloud tool already installed, so you install nothing on your Mac. Cloud Shell itself is far too small to run Cuttlefish; it is only where you type commands.

Cloud Shell

gcloud compute instances create mfarm-lab \
  --zone=asia-south1-c \
  --machine-type=n2-standard-16 \
  --enable-nested-virtualization \
  --image-family=ubuntu-2404-lts-amd64 \
  --image-project=ubuntu-os-cloud \

What each line is choosing, since these are the decisions that matter:

FlagWhy this value
asia-south1-cMumbai. Closest to you, so SSH feels responsive.
n2-standard-1616 cores / 64 GB. SwiftShader renders on the CPU, so cores are the resource that matters. N2, not E2 — E2 cannot do nested virtualisation at all.

If it refuses

Quota errors are the usual first failure — trial accounts get a modest CPU allowance per region. Drop to --machine-type=n2-standard-8 and continue; 8 cores is enough for one device, which is all M1 and M2 need. If the flag itself is rejected, your gcloud is old — run gcloud components update, or create the VM through the console UI where the setting lives under Advanced options → CPU platform and GPU → Enable nested virtualization.

B4

Connect, and check the gate

~5 minutes · M0

In the console go to Compute Engine → VM instances and click SSH next to mfarm-lab. A terminal opens in a browser tab with keys handled for you — nothing to configure.

on the VM

Hard stop

You need /dev/kvm to exist, the egrep count to be greater than zero, and kvm-ok to say KVM acceleration can be used. If any of those fail, the VM was created without nested virtualisation and no amount of configuration will fix it. Delete it (step B11) and recreate it with the flag. Nothing below this line is worth attempting first.

That's M0. Tick it.

B6

Bootstrap Cuttlefish

~30–60 minutes, mostly waiting · M1

Our script does the work: installs the Cuttlefish Debian packages, adds you to the kvm, cvdnetwork and render groups, downloads a prebuilt Android image, then boots one device as a smoke test. It runs in two phases with a reboot between them, because group membership does not apply to a shell that is already running.

Why it no longer builds from source

The script installs prebuilt packages from Google's Artifact Registry, and only falls back to building from source if that fails. This is not just a speed optimisation. Building drives Bazel to download external dependencies from GitHub, GitHub rate-limits those per source IP, and cloud VM IP ranges are shared with thousands of other machines — so the build fails with 429 Too Many Requests on traffic that is not yours. Credentials do not help, because codeload.github.com does not honour them for archive downloads. We hit this on the first attempt and retrying with backoff did not clear it. Artifact Registry is a different host with no such limit.

CF_INSTALL=source forces the old build path if you ever need it; CF_INSTALL=prebuilt makes a registry failure stop the script rather than quietly starting an hour-long build.

on the VM — phase 1
cd ~/mfarm
./spikes/bootstrap_cuttlefish.sh
# it will stop and tell you to reboot
sudo reboot

The browser SSH tab will disconnect. Wait about thirty seconds, reopen it, and run the same command — the script keeps state in ~/.mfarm_bootstrap and resumes rather than redoing work.

on the VM — phase 2, after reboot
cd ~/mfarm
./spikes/bootstrap_cuttlefish.sh
Prove the image is real Android 17 later, not now

The script defaults to the aosp-main branch. Our plan targets Android 17 (android-17.0.0_r1), but do not fight two unknowns at once — get anything booting first. Once it does, re-run pinned to the release branch with BRANCH=... ./spikes/bootstrap_cuttlefish.sh, and confirm with adb -s 0.0.0.0:6520 shell getprop ro.build.version.release.

When it prints READY with a cold-boot time, that is M1. Write the number down — it is the baseline every later reset time is compared against.

B7

Snapshot and restore

~30 minutes · M2

This is the load-bearing one. Our entire reset story — “a released device is restored from a snapshot in about three seconds rather than cold-booted in thirty-five” — depends on it, and it only works with a software GPU. Two flags are mandatory and the smoke test above did not use them.

on the VM
cd ~/cf/image
cvd stop || true

# The two flags that buy snapshot support.
cvd start --daemon \
  --gpu_mode=guest_swiftshader \
  --enable_virtiofs=false \
  --report_anonymous_usage_stats=n

# wait for it, then take a snapshot
adb -s 0.0.0.0:6520 wait-for-device
adb -s 0.0.0.0:6520 shell getprop sys.boot_completed

cvd snapshot_take --snapshot_path=$HOME/cf/snap1

# now restore it, and TIME it — this number is the whole point
cvd stop
time cvd start --daemon --snapshot_path=$HOME/cf/snap1
adb -s 0.0.0.0:6520 shell getprop sys.boot_completed
What to record
  • Did snapshot_take succeed, and how long did it take?
  • How many seconds did the restore take? Compare with your M1 cold boot.
  • Did the restored device actually work — can adb shell still drive it?
  • Any complaint about the two flags. If snapshot support has moved upstream, this is exactly the known-issue-1 finding, and it is worth the whole day on its own.
B8

Appium, for real

~2–3 hours · M3 — the deliverable

Everything runs on this one machine: Postgres, the control plane, the worker agent and Appium. That is fine — the production compose stack binds only to loopback, so it all talks to itself.

Since 2026-08-18 this is one command

deploy/farm-up.sh does everything in this step — preflight, secrets, compose, the password reconcile, the seed, and the worker in tmux — and is idempotent, so re-running is the normal way to use it. Prerequisites are the same: docker, node, and step B6 already done. Use CF_INSTANCES=2 for B9.

The blocks below are what it does, and they stay here because when something disagrees you need to run the pieces by hand. The script was written after this runbook, precisely because typing these out on a box billing ~₹65/hour is the wrong place to be careful.

Bring up the control plane

on the VM
cd ~/mfarm
sudo apt-get install -y docker.io docker-compose-v2 tmux

# Node 22, NOT `apt-get install nodejs` — Ubuntu 24.04 ships 18.x, which has no native TypeScript
# stripping, and the worker then dies on its first .ts import with an error naming nothing useful.
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs
sudo usermod -aG docker $USER && newgrp docker

# throwaway secrets — never the ones a real farm would use
mkdir -p deploy/secrets && chmod 700 deploy/secrets
openssl genpkey -algorithm ed25519 -out deploy/secrets/session_signing_key.pem
openssl pkey -in deploy/secrets/session_signing_key.pem -pubout \
  -out deploy/secrets/session_public_key.pem
openssl rand -base64 32 | tr -d '/+=' > deploy/secrets/worker_registration_token
printf '%s' "$(openssl rand -base64 32 | tr -d '/+=')" > deploy/secrets/metrics_token
printf '%s' "$(openssl rand -base64 24 | tr -d '/+=')" > deploy/secrets/grafana_admin_password
chmod 600 deploy/secrets/*

cp deploy/.env.example deploy/.env
nano deploy/.env        # fill POSTGRES_PASSWORD and APP_DB_PASSWORD with anything

docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
curl -fsS http://127.0.0.1:3000/health && echo

Then make the database agree with the password you chose — the control plane refuses to start against the committed development password, deliberately.

on the VM
docker exec -i mfarm-postgres-1 psql -U mfarm -d mfarm \
  -c "ALTER ROLE mfarm_app WITH PASSWORD ''"
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env restart api

Seed the database, or nothing below will work

A freshly migrated database has the schema and nothing in it. Two things are missing and neither announces itself usefully: the regions table is empty, and hosts.region is a foreign key into it — so worker registration fails on a constraint violation rather than on anything that names the problem. And no tenant API key exists, so every route except the health probes refuses you.

on the VM
cd ~/mfarm
eval "$(DATABASE_URL="postgres://mfarm:$POSTGRES_PASSWORD@127.0.0.1:5432/mfarm" \
        REGION=lab node apps/api/scripts/seed-lab.mjs)"

echo "$MFARM_API_KEY"     # mfk_… — shown once, only its hash is stored
echo "$MFARM_REGION"      # lab
Found before you paid for it

seed-lab.mjs did not exist until this runbook was written — the gap was found by checking the commands against the code rather than by discovering it on a metered box. It is idempotent: re-running reuses the region and org and mints an additional key.

cd ~/mfarm && npm install

If it says “Cuttlefish unavailable”

The agent falls back to the AVD tier and asks for AVD_NAME, which is not what we are testing. That message means CuttlefishDevice.available() said no — check CF_IMAGE_DIR points at the directory containing the unpacked image, and that cvd is on PATH in this shell.

In a second SSH tab, confirm the control plane can actually see a device before you try to drive one. $MFARM_API_KEY came from the seed step — re-run the eval line in the new tab to have it there too.

second tab
curl -s -H "Authorization: Bearer $MFARM_API_KEY" \
  http://127.0.0.1:3000/v1/devices | head -40

# and watch the farm's own metrics while you work
curl -s -H "Authorization: Bearer $(cat ~/mfarm/deploy/secrets/metrics_token)" \
  http://127.0.0.1:9464/metrics | grep '^mfarm_devices'
This is where disagreement is expected

The hub has never spoken to a real Appium server and the supervisor has never supervised one. When something disagrees here, capture the exact request and response — that is a repo bug worth fixing properly, not something to work around on the box. The mfarm_devices and mfarm_sessions gauges above tell you what the control plane believes, which is usually the fastest way to see where reality diverged.

Then point a real suite at it. If the fleet reports a READY device and one unmodified Appium test goes green through MFARM_WEBDRIVER_URL, that is M3, and it is the single most valuable thing this project has ever produced.

B9

Two devices

~1 hour · M4

on the VM
cd ~/cf/image
cvd stop || true
cvd start --daemon --num_instances=2 \
  --gpu_mode=guest_swiftshader --enable_virtiofs=false \
  --report_anonymous_usage_stats=n

adb devices        # expect 0.0.0.0:6520 AND 0.0.0.0:6521

Then restart the worker with CF_INSTANCES=2 so it registers both.

Two serials means the worker's per-device systemPort and mjpegServerPort derivation gets its first real test, and the control plane should show two allocatable devices. Run the suite sharded across both. Watch CPU with htop — SwiftShader is CPU-bound and two devices on 16 cores is the first honest look at what this box can hold.

B10

Save the work before you destroy it

~5 minutes · the optimisation that matters

Bootstrapping takes one to two hours, almost all of it downloading. Do it once. A disk snapshot is compressed, incremental and costs a few rupees a month, and every future session starts from a machine that already has Cuttlefish installed and the image downloaded.

Cloud Shell
gcloud compute disks snapshot mfarm-lab \
  --zone=asia-south1-c \
  --snapshot-names=mfarm-cf-ready

Next session, recreate from it instead of starting over:

Cloud Shell — next time
gcloud compute disks create mfarm-lab \
  --source-snapshot=mfarm-cf-ready \
  --zone=asia-south1-c --type=pd-balanced

gcloud compute instances create mfarm-lab \
  --zone=asia-south1-c \
  --machine-type=n2-standard-16 \
  --enable-nested-virtualization \
  --disk=name=mfarm-lab,boot=yes,auto-delete=yes

Also copy off anything you want to keep — logs, timings, notes:

from your Mac or Cloud Shell
gcloud compute scp --recurse \
  mfarm-lab:/tmp/cf_start.log mfarm-lab:/tmp/cf_build.log . \
  --zone=asia-south1-c
B11

Destroy everything

~2 minutes · never skip this

Cloud Shell
gcloud compute instances delete mfarm-lab --zone=asia-south1-c --quiet

# the step people forget — a disk can outlive its machine and keeps billing
gcloud compute disks list
gcloud compute instances list
gcloud compute snapshots list      # snapshots are cheap; keep mfarm-cf-ready
The end-of-session check

instances list must be empty. disks list must be empty, or contain only disks you consciously decided to keep. If a disk is listed and you do not know why it is there, delete it: gcloud compute disks delete NAME --zone=asia-south1-c. Keeping mfarm-cf-ready as a snapshot is correct and costs almost nothing.

Then look at the credit balance on the console home page. After a full day it should have moved by single-digit dollars. If it moved more, something is still running.

99 — Recovery

When it goes wrong

It will. These are the failures I expect, in the order you are likely to hit them.

/dev/kvm is missing on the VM

Nested virtualisation was not enabled, or you picked an E2 machine type, or an Arm one. It cannot be turned on afterwards. Delete the instance and recreate it with --enable-nested-virtualization and an N2 machine type.

Quota exceeded when creating the instance

Trial accounts get a limited CPU allowance per region. Use --machine-type=n2-standard-8, or try a different zone (asia-south1-a, asia-south1-b). Eight cores is enough for M0 through M3; only M4 and M5 really want sixteen.

The bootstrap script dies while building the Debian packages

This is known issue 1 arriving on schedule — upstream android-cuttlefish changes its build steps. The script writes the full log to /tmp/cf_build.log and prints the last 25 lines. Send me that, plus the current upstream README, and we fix the script in the repo rather than patching it on a box you are about to delete.

“not in group 'kvm' yet”

The reboot did not happen or you reconnected to an old shell. Run sudo reboot, wait thirty seconds, open a fresh SSH tab, and check with id -nG. You need kvm, cvdnetwork and render.

The device never reaches boot_completed

Read /tmp/cf_start.log and the per-instance logs under ~/cf/image/cuttlefish/instances/*/logs/. Common causes: not enough RAM (check free -g), a partly downloaded image (delete ~/cf/image and refetch), or a flag upstream no longer accepts. Try booting with no extra flags first to isolate which.

Everything works but the control plane shows no devices

That is our bug, not Cuttlefish's, and it is a good find. Check the worker registered (POST /v1/workers/register in its output), then read the metrics endpoint in step B8 — mfarm_devices tells you what the control plane believes and mfarm_hosts whether the worker is heartbeating at all. Capture both and send them.

I am out of time / it is going badly

Snapshot the disk (B10), destroy the machine (B11), and stop. The snapshot means the next session resumes rather than restarts. A session that ends at M1 with a clear note about what broke is worth more than a rushed one that ends confused.

What to write down, wherever you stop

Add findings to HANDOFF.md and docs/MVP_PLAN.md the same day — the repo is this project's memory, and a fact that lives only in a terminal scrollback is a fact you will pay to rediscover.

  • The cvd flags that actually worked, verbatim, and any that did not.
  • Cold-boot seconds, and snapshot-restore seconds beside them.
  • Whether guest_swiftshader plus enable_virtiofs=false really gives working snapshots.
  • Every place the real Appium disagreed with our hub or supervisor.
  • “nested virt, n2-standard-16” written next to any performance number — a future reader must not mistake it for bare-metal.
