MFARM CONSOLE · 02

The frame system

Ceramic direction, built as a function of reported geometry. Four profiles today and a rule for the fifth. The frame is an MFARM asset and may be as premium as we can make it; the screen is the device's own framebuffer and is never simulated.

Two objects, one rule

The frame
Chassis, bezel, corner radius, cutout, side rails, edge highlight, contact shadow. Ours to draw. Everything premium about the session screen lives here.
The screen
The real-time framebuffer from the running Android instance. Every pixel comes from the device. No placeholder wallpaper, no mocked status bar, no fake app.
The implementation rule that keeps them separate
The frame is additive around the panel box, never drawn over it. Bezel is padding on the chassis; rails are positioned outside the chassis edge; the contact shadow is a sibling below it. The only element that overlaps the panel is the punch-hole, which is physically accurate — a real camera does occlude pixels, and Android reserves that region. It must be centred and sized from geometry so it never lands on status-bar content. The current frame fails this: in the reference capture the panel's own edge clips the status-bar clock.

Geometry drives everything

Nothing is hand-placed per device. The console already knows panel resolution, density, dp width and a profile id; every dimension below is derived from those. Values are given as a ratio of rendered panel width, plus the resolved pixel value at a 300px render — scale linearly for any stage size.

Panel aspect ratio is reportedWidth / reportedHeight, always. A 720×1280 device is visibly stubbier than a 1080×2340 one, and it must be — screen shape is the reason someone chose a device, so the frame is where that difference becomes visible before the user starts testing.

Resolving a profile
frameFor(device) { const p = profiles[device.profileId]; // real profile table if (device.tier === 'physical') return physicalFrame(device, p); if (!p) return neutralFrame(device); // geometry only return virtualFrame(device, p); // X1 Pro | X1 } // every frame returns the same shape, so the stage never branches { bezel, panelRadius, chassisRadius, cutout, cutoutInset, rails: [...], chassisFill, edgeHighlight, aspect }
One return shape for all four cases means the session stage has no per-device conditionals — add a profile row and a new device gets a correct frame with no frontend change. CONFIRM the profile table exposes dp width and a tier discriminator alongside panel geometry.

Why the unprofiled frame has no cutout
Because we do not know where its camera is. Drawing one would be inventing data, and the whole point of the neutral chassis is that it is honest about what the farm knows: geometry, nothing more. It reads as a deliberate industrial enclosure rather than a failed phone.
Why the physical handset looks different
It is a different kind of object — a real machine somebody can unplug, with a different reset story and no snapshot. Squarer corners, the thinnest bezel in the family, a warmer rail, and the REAL DEVICE badge. Nobody should ever mistake which they are holding.

Implementation

The whole frame is six nested elements and no images. It costs one paint and never composites over the panel, which matters because rendering is software and frame rate is the proof the session is healthy.

<div class="mf-device" data-profile="x1-pro" data-state="live"> <div class="mf-chassis"> <!-- padding: bezel; radius: chassisRadius --> <i class="mf-edge"></i> <!-- inset 2px, 1px warm highlight ring --> <i class="mf-rail" data-rail="power"></i> <i class="mf-rail" data-rail="volume"></i> <div class="mf-glass"> <!-- radius: panelRadius; overflow: hidden --> <video class="mf-panel"></video> <!-- the framebuffer. nothing else in here --> <i class="mf-cutout"></i> <i class="mf-sheen"></i> </div> </div> <i class="mf-contact"></i> <!-- sibling, below. the grounded shadow --> </div> .mf-chassis { background: linear-gradient(160deg, ...ceramic stops); box-shadow: var(--e-device); transition: box-shadow var(--m-settle) var(--ease-out); } [data-state="off"] .mf-chassis, [data-state="waking"] .mf-chassis { box-shadow: var(--e-device-flat); } .mf-sheen { background: linear-gradient(202deg, rgba(255,246,235,.07), transparent 50%); mix-blend-mode: screen; opacity: var(--glass-sheen); pointer-events: none; } .mf-panel { display: block; width: 100%; aspect-ratio: var(--panel-aspect); }
Performance rules
No backdrop-filter anywhere near the stage. No animated box-shadow or filter while the stream is live — the two shadow states cross-fade once, on attach, and never again. mf-sheen is a static gradient, not a moving highlight. The panel element itself gets no transform, so the video layer stays on its own compositor layer.
The sheen tradeoff DECIDE
The glass sheen tints real pixels by 6–7% at the top edge. It is most of what makes the frame read as glass rather than a hole. Ship it as --glass-sheen defaulting to .07, with a settings toggle to 0 for anyone doing visual comparison work, where a tint over the framebuffer is unacceptable.
